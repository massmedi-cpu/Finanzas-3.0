# REC-AUTH-204–206 · metadatos de conexión Google protegidos por sesión

19/10/2026. Financial App, PR #619 DRAFT; no cambia producción ni originales bancarios.

## Hallazgo comprobado con la preview Vercel del SHA 19868ef

Con autorización para abrir la preview protegida de Vercel, **sin sesión de Financial App**, el GET `/api/source/google/status` devolvía HTTP 200 e incluía `connection` con campos de correo y nombre de archivo. No se han copiado ni divulgado esos valores. Las peticiones GET al estado de sincronización y health devolvían 503, mientras el log Edge indicaba `workspace_context_required`: no era una prueba de caída de base sino ausencia de identidad de workspace.

## Corrección de mínimo privilegio

- `GET` y `DELETE /api/source/google/status` exigen sesión propia **antes** de revelar si Google está configurado o consultar cualquier conexión.
- Una cookie no basta: la identidad debe validarse mediante `source.capabilities` en el gateway financiero, que verifica el token Auth y la membresía del workspace y aplica `SET ROLE financial_app_gateway`. Los rechazos se devuelven con códigos públicos genéricos, sin texto SQL, cuenta ni nombre de archivo.
- GET `/api/health/source-runtime` y GET `/api/source/google/sync` devuelven HTTP 401 al visitante anónimo y distinguen la denegación de membresía HTTP 403 frente a un fallo de infraestructura HTTP 503.
- Dos pantallas Fuente bancaria muestran el motivo de autenticación y un enlace a `/login?next=/configuration/source` sin habilitar escrituras.
- Casos REC-AUTH-204 (UI sintética) y 205–206 (GET reales sin cookie). Las suites no ejecutan POST ni DELETE.

## Verificación y límites

Repetir los tres GET sin sesión en preview del nuevo SHA y exigir 401, **sin connection, cuenta, capabilities, run, cursors**. CI completa sobre HEAD nuevo obligatoria. No basta para certificar el acceso correcto de dos usuarios autenticados, los permisos IDOR ni un backend cloud aislado. AP1/AP2 y publicación siguen abiertas; producción intacta.
