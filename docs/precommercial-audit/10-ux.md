# 10 · Auditoría UX

## Dictamen

Financial App tiene buenos flujos dentro de cada módulo, pero la experiencia global sigue dependiendo demasiado de que el usuario conozca la arquitectura interna. El problema principal no es “no se puede hacer”, sino **saber dónde hacerlo, volver entre áreas y entender qué requiere atención ahora**.

## Recorridos auditados

### Usuario nuevo

Estado actual esperado:
1. Login.
2. Configuración / Fuente.
3. Conectar Google o usar conexión gestionada.
4. Comprobar estado/runtime.
5. Primera prevalidación.
6. Sincronizar.
7. Volver a Inicio.
8. Descubrir cuentas, movimientos, presupuestos, recurrentes y previsión por separado.

**Problema:** el flujo es técnicamente seguro, pero demasiado cercano a una consola de administración. No existe una experiencia de activación que traduzca estos pasos a objetivos de usuario.

### Usuario habitual

Estado actual:
1. Inicio.
2. Revisar balance/previsión/actividad.
3. Entrar manualmente en Movimientos si hay algo que corregir.
4. Ir a Recurrentes si quiere validar patrones.
5. Volver a Previsión para actualizar/conciliar.
6. Ir a Documentos para pendientes documentales.

**Problema:** las tareas de atención están repartidas y el usuario debe recordar en qué módulo vive cada una.

### Usuario avanzado

Estado actual:
- Movimientos ofrece filtros separados de su estado aplicado, paginación, edición individual, edición masiva, revisión de duplicados y transferencias.
- Previsión permite periodo, manuales, exclusión, búsqueda de candidato real y conciliación.
- Recurrentes permite confirmar/ignorar/recalcular.

**Fortaleza:** la profundidad existe y las operaciones peligrosas requieren acción explícita.

**Problema:** la navegación entre motores relacionados y los estados globales de trabajo no están unificados.

## Fortalezas UX verificadas

1. **Cambios manuales transparentes.** Movimientos comunica que se aplican como overrides y no alteran la fuente bancaria.
2. **Acciones masivas reales.** El usuario no necesita editar movimiento por movimiento para categoría/estado.
3. **Separación draft/applied filters.** Evita que cada pulsación lance una búsqueda costosa y permite construir un filtro compuesto antes de aplicarlo.
4. **Recurrentes no se auto-confirman.** La app presenta confianza y exige decisión explícita.
5. **Previsión permite reconciliar con movimiento real.** Es un flujo útil y trazable, no una predicción desconectada.
6. **Fuente bancaria falla cerrada.** Si algo no cumple contrato, el usuario recibe error y no se persiste como éxito.
7. **Estados de carga/error/éxito** están presentes en las superficies críticas.

## Hallazgos

### UX-001 — P1 comercial · No existe onboarding orientado a resultado

**Área:** Primera experiencia  
**Evidencia:** el flujo inicial disponible es login + Configuración/Fuente, donde aparecen conceptos técnicos y controles de preflight/sync.  
**Consecuencia:** un usuario nuevo debe entender arquitectura antes de obtener su primer beneficio.  
**Recomendación:** onboarding progresivo con objetivos, no con infraestructura: conectar datos → verificar que son correctos → confirmar cuentas → mostrar primer resumen → presentar tareas pendientes. Mantener diagnóstico técnico accesible aparte.  
**Esfuerzo:** Alto.  
**Riesgo de regresión:** Bajo si consume motores existentes.  
**Prioridad:** P1 comercial.  
**Criterio de aceptación:** beta tester no técnico completa la primera configuración sin documentación externa ni vocabulario de desarrollo.

### UX-002 — P1 · No existe una cola unificada de “Para revisar”

**Área:** Gestión de atención  
**Evidencia:** existen `reviewState`, duplicados, transferencias, candidatos recurrentes, documentos pendientes, diferencias de saldo, avisos de sync y elementos de previsión con confianza; cada uno vive en su módulo.  
**Consecuencia:** el usuario debe recordar dónde mirar. La app detecta problemas, pero no organiza su trabajo.  
**Recomendación:** agregador read-only de referencias con prioridad/origen y deep-link exacto al elemento. No duplicar estados ni crear otra fuente de verdad. Inicio muestra sólo los principales.  
**Esfuerzo:** Medio.  
**Riesgo de regresión:** Bajo.  
**Prioridad:** P1 UX/P2 técnico.  
**Criterio de aceptación:** el usuario habitual puede saber en una sola pantalla si queda algo importante por revisar y llegar directamente al elemento.

### UX-003 — P1/P2 · Navegación obliga a usar Inicio como estación intermedia

**Área:** Navegación  
**Evidencia:** cada módulo implementa enlaces de regreso y navegación local; no existe AppShell persistente. Inicio tiene quickNav, pero fuera de Inicio no existe una navegación primaria uniforme.  
**Consecuencia:** cambiar de Movimientos a Presupuestos, Documentos o Cuentas normalmente exige volver a Inicio o conocer enlaces específicos.  
**Recomendación:** AppShell responsive con destinos primarios persistentes y secundarios agrupados. Conservar deep-links contextuales entre módulos relacionados.  
**Esfuerzo:** Medio/alto.  
**Riesgo de regresión:** Medio.  
**Prioridad:** P1 percepción/UX, P2 técnico.  
**Criterio de aceptación:** desde cualquier módulo se llega a cualquier destino principal sin usar Inicio como paso obligatorio.

### UX-004 — P2 · Relación Recurrentes → Previsión requiere pasos manuales evitables

**Área:** Flujo entre módulos  
**Evidencia:** Previsión enlaza a Recurrentes y dispone de “Actualizar recurrentes”. Recurrentes permite confirmar un candidato, pero la decisión no devuelve al usuario al impacto concreto en Previsión ni actualiza automáticamente la pantalla que originó la tarea.  
**Consecuencia:** el usuario confirma una recurrencia, vuelve a Previsión y debe ejecutar/esperar la regeneración para ver su efecto.  
**Recomendación:** deep-link contextual y CTA posterior: “Recurrencia confirmada · ver impacto en Previsión”. La regeneración puede dispararse de forma explícita y segura desde ese contexto, manteniendo trazabilidad.  
**Esfuerzo:** Bajo/medio.  
**Riesgo de regresión:** Bajo.  
**Prioridad:** P2.  
**Criterio de aceptación:** confirmar una recurrencia desde un flujo iniciado en Previsión permite volver a su impacto futuro en un paso.

### UX-005 — P2 · Movimientos puede perder contexto tras guardar

**Área:** Continuidad de tarea  
**Evidencia:** `patchTransactions()` vuelve a cargar desde la primera página con los filtros aplicados y elimina selección/edición/review. En listas grandes, el movimiento editado puede cambiar de posición o quedar fuera del lote visible.  
**Consecuencia:** después de editar/revisar, el usuario puede perder el punto visual donde estaba trabajando, especialmente en sesiones de limpieza largas.  
**Recomendación:** mantener ancla/foco del movimiento cuando siga cumpliendo filtros; si sale del filtro, comunicarlo (“Ya no aparece porque quedó Confirmado”) y ofrecer deshacer/ver cambio.  
**Esfuerzo:** Medio.  
**Riesgo de regresión:** Bajo/medio.  
**Prioridad:** P2.  
**Criterio de aceptación:** tras editar, el usuario entiende dónde quedó el elemento y continúa con el siguiente sin reconstruir manualmente el contexto.

### UX-006 — P2 · Recuperación de errores globales insuficiente

**Área:** Error recovery  
**Evidencia:** Inicio, ante fallo de sus cinco cargas, ofrece “Abrir Cuentas”; no existe botón de reintento global. No hay `app/error.tsx`. Los módulos sí ofrecen mensajes específicos, pero la recuperación varía.  
**Consecuencia:** un error temporal puede empujar al usuario a otro módulo sin resolver la causa o forzar reload manual.  
**Recomendación:** política uniforme: explicar → reintentar → alternativa segura. Global `error.tsx` y estados locales con CTA Reintentar cuando la operación sea idempotente.  
**Esfuerzo:** Bajo/medio.  
**Riesgo de regresión:** Bajo.  
**Prioridad:** P2.  
**Criterio de aceptación:** todos los errores temporales recuperables ofrecen reintento sin perder datos introducidos.

### UX-007 — P2 · Filtros de Movimientos no reflejan claramente cambios sin aplicar

**Área:** Filtros / feedback  
**Evidencia:** existen `draftFilters` y `appliedFilters`, lo cual es técnicamente correcto, pero la interfaz depende del botón Aplicar. El contador se calcula sobre `appliedFilters`; no hay un indicador explícito de “cambios de filtro pendientes de aplicar” en el estado revisado.  
**Consecuencia:** el usuario puede cambiar varios controles y creer que la tabla ya representa esos valores antes de pulsar Aplicar.  
**Recomendación:** indicador/estado de dirty filters y deshabilitar Aplicar cuando no hay cambios. En búsqueda de texto se puede valorar Enter; no lanzar peticiones en cada tecla sin necesidad.  
**Esfuerzo:** Bajo.  
**Riesgo de regresión:** Muy bajo.  
**Prioridad:** P2.  
**Criterio de aceptación:** siempre es evidente si la tabla refleja o no los valores visibles en los filtros.

### UX-008 — P2 · Demasiada explicación técnica compite con las acciones

**Área:** Carga cognitiva  
**Evidencia:** varias pantallas explican motores centrales, fuente de verdad, fases, runtime, contrato y principios. Esa información es correcta y valiosa para auditoría.  
**Consecuencia:** las decisiones principales compiten con contenido de diagnóstico y el usuario lee más antes de actuar.  
**Recomendación:** información financiera en primer nivel; “Cómo se calcula / Detalles técnicos” desplegable en segundo nivel. No eliminar trazabilidad, sólo jerarquizarla.  
**Esfuerzo:** Medio de copy/UI.  
**Riesgo de regresión:** Bajo.  
**Prioridad:** P2.  
**Criterio de aceptación:** las acciones principales y el estado financiero se entienden sin leer documentación técnica, que sigue disponible bajo demanda.

### UX-009 — P2 · Login no asocia el error al grupo de campos ni mueve foco

**Área:** Formularios / recuperación  
**Evidencia:** login muestra un `<p role="alert">`, pero los inputs no reciben `aria-invalid`, `aria-describedby` ni foco cuando falla autenticación/validación.  
**Consecuencia:** visualmente el mensaje se ve, pero lectores de pantalla y usuarios de teclado reciben menos contexto sobre dónde continuar.  
**Recomendación:** error general con id y `aria-describedby` en el formulario/campos relevantes; al error, foco en el mensaje o en email según tipo. No revelar cuál credencial concreta es incorrecta.  
**Esfuerzo:** Bajo.  
**Riesgo de regresión:** Muy bajo.  
**Prioridad:** P2, enlaza con Accesibilidad.  
**Criterio de aceptación:** error anunciado, foco predecible y credenciales no enumerables.

## Principio UX resultante

La aplicación debe avanzar hacia este ciclo:

**Ver qué importa → resolver pendientes → comprender por qué → decidir → anticipar → volver con el contexto preservado.**

No añadir pantallas si un deep-link, un agregador o una mejor jerarquía resuelve el problema.
