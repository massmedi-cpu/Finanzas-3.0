# REC-SYNC-200 a 203 · Un HTTP 200 no certifica una importación bancaria

Fecha: 19/10/2026. PR #619, sin modificaciones del origen ni base de producción.

## Hallazgo reproducido por inspección
Las pantallas `/configuration/source` y su vista diagnóstica trataban la respuesta de preflight y la sincronización posterior como válidas si el HTTP era 200, sin verificar que el cuerpo contuviera resumen canónico y contadores completos. En un 200 malformado, la importación podía continuar o la interfaz afirmar éxito y «sin cambios nuevos» sin haber comprobado el resultado.

## Cambio acotado
`src/application/source-confirmation-contract.ts` introduce dos validadores puros, compatibles con cliente: preflight con identidad/revisión, SHA-256, cuentas y cursores coherentes en el total, fechas/saldos bien tipados; y recibo de sincronización `success` con identificador, contadores enteros y conservación de filas vistas. Ambas pantallas rechazan fallando cerrado el cuerpo malformado; antes del sync bloquean el POST, después del sync no repiten automáticamente el POST y consultan el estado persistido si la respuesta es incierta. Ni el código backend ni la fuente bancaria se reescriben.

## Pruebas
- REC-SYNC-200: preflight HTTP 200 inválido, 0 POST de sync.
- REC-SYNC-201: sync HTTP 200 con importe/counter mal tipado, 1 POST y GET posterior, 0 éxito aparente.
- REC-SYNC-202: resumen real de `buildOfficialSourcePreflightSummary` válido y variantes dañadas rechazadas.
- REC-SYNC-203: recibo transaccional válido frente a parcial, contador inválido, cuenta inconsistente e ID ausente.

CI obligatoria de HEAD, navegador y aceptación AP1–AP8 se mantienen abiertas. No sustituye backup y restauración, ejecución de preflight sobre snapshot completo ni autorización de importación real.
