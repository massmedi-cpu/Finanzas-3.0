# V2.6.0 — Motor de reglas privadas reversible

## Objetivo

Consolidar el motor privado de reglas de Financial App como capa de automatización trazable para los movimientos, preservando siempre la fuente bancaria y las ediciones manuales posteriores.

La implementación canónica es la existente en `FINANCIAL_APP_1.6.0_RULES_ENGINE.sql` y la superficie de aplicación `/reglas` + `/api/rules`. Este documento describe esa implementación real y sustituye una especificación antigua basada en objetos ya retirados, que ya no corresponde al código ni a Supabase.

## Precedencia y protecciones

1. El origen bancario nunca se reescribe.
2. Los duplicados y movimientos cuyo origen ha desaparecido quedan excluidos del motor.
3. Una edición manual posterior a una regla tiene prioridad y no se revierte.
4. Las reglas solo modifican la capa editable de `financial_app.transactions`.
5. Cada aplicación conserva los valores `before` y `after` necesarios para una reversión segura.
6. `Deshacer` solo restaura un campo si la regla todavía controla exactamente el valor aplicado; si el usuario lo modificó después, se conserva.
7. La aplicación a movimientos existentes está limitada a 5.000 coincidencias por ejecución y devuelve si el límite se alcanzó.

## Tablas canónicas

- `financial_app.transaction_rules`
  - definición de condición/acción;
  - prioridad y estado activo;
  - `stop_processing` para detener reglas posteriores.
- `financial_app.transaction_rule_applications`
  - registro de cada aplicación sobre un movimiento;
  - cambios por campo;
  - origen, actor, fecha y estado de reversión.
- `financial_app.transaction_rule_history`
  - historial de creación, actualización, reactivación y desactivación de reglas.

Las tres tablas tienen RLS activado. En el estado auditado de Supabase no conceden privilegios directos a `anon`, `authenticated` ni `service_role`; el acceso se realiza mediante las funciones autorizadas.

## Funciones internas

- `rules_overview_core()` — lectura estable del estado del motor.
- `preview_rule_core(p_rule, p_limit)` — previsualización `STABLE`, sin escrituras.
- `normalize_rule_definition_core(p_rule)` — valida y normaliza la definición.
- `rule_matches_transaction_core(...)` — decide coincidencia.
- `rule_candidate_changes_core(...)` — calcula cambios permitidos respetando protecciones.
- `apply_rule_to_transaction_internal(...)` — aplica cambios sobre la capa editable y registra trazabilidad.
- `apply_rule_existing_core(p_rule_id)` — aplica una regla a movimientos existentes con límite de 5.000.
- `upsert_rule_core(...)` — alta/edición/reactivación con historial.
- `deactivate_rule_core(...)` — desactiva sin borrar trazabilidad.
- `revert_rule_applications_core(...)` — reversión segura por campo.
- `rule_field_has_later_user_edit(...)` — protege cualquier edición manual posterior.
- `apply_rules_after_insert_trigger()` — automatización para nuevos movimientos.

Todas las funciones `SECURITY DEFINER` del motor validan `financial_app.authorized_email()` antes de exponer o modificar datos privados.

## RPC públicas usadas por la aplicación

- `financial_app_rules_overview()` — lectura.
- `financial_app_preview_rule(p_rule)` — lectura/previsualización.
- `financial_app_upsert_rule(p_rule_id, p_rule)` — crear o editar.
- `financial_app_apply_rule(p_rule_id)` — aplicar a existentes.
- `financial_app_deactivate_rule(p_rule_id)` — desactivar.
- `financial_app_revert_rule(p_rule_id)` — deshacer aplicaciones activas de forma segura.

`/api/rules` requiere una sesión autorizada mediante `getAuthorizedClient`, valida el cuerpo como `unknown` y solo permite las acciones anteriores.

## Interfaz

`/reglas` permite:

- crear y editar reglas;
- definir prioridad, filtros por contraparte/concepto/tipo/categoría/cuenta/importe/dirección;
- establecer categoría, subcategoría, etiquetas y recurrencia;
- previsualizar coincidencias antes de aplicar;
- aplicar a movimientos ya existentes de forma explícita;
- desactivar/reactivar;
- deshacer de forma segura.

## Evidencia auditada

Durante la auditoría integral de V2.6:

- el árbol activo completo entra en `audit:v260`;
- las tres tablas del motor tienen RLS activo;
- los privilegios directos de las tablas están restringidos al propietario `postgres`;
- las funciones internas de lectura son `STABLE` y las de mutación son `VOLATILE`;
- todas las funciones internas de acceso relevante comprueban `authorized_email()`;
- el endpoint web está protegido por sesión autorizada;
- la fuente bancaria continúa siendo de solo lectura;
- las fechas y periodos de la aplicación usan la utilidad canónica `Europe/Madrid`, con límites de día, mes y año cubiertos por pruebas de regresión;
- las regresiones 1.7 → 2.5, el formato es-ES, TypeScript y el build deben permanecer verdes antes de cerrar V2.6.

## Rollback funcional

Desactivar una regla impide nuevas aplicaciones sin eliminar el historial. `Deshacer` procesa las aplicaciones vigentes y revierte únicamente los campos que no hayan sido modificados manualmente después. El origen bancario no se altera en ningún caso.
